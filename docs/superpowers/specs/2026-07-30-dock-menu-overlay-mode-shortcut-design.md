# Dock 菜单与浮层模式快捷键设计

## 目标

在不改变录音、全屏截图、回答滚动和浮层显示效果的前提下：

- macOS 菜单栏不再创建 Helper 的紫色状态图标。
- 原菜单迁移到 Helper 的 Dock 图标右键菜单，继续提供浮层显示/隐藏、输入/穿透模式切换和退出。
- 新增 `Fn+Tab` 全局快捷键，用于切换浮层的输入模式和穿透模式。
- 现有四组 Fn 快捷键保持不变。

## 快捷键

| 快捷键 | 功能 |
| --- | --- |
| `Fn+Control` | 开始/停止录音 |
| `Fn+Shift` | 全屏截图 |
| `Fn+Option` | 开启/关闭回答滚动模式 |
| `Fn+Command` | 显示/隐藏浮层 |
| `Fn+Tab` | 切换输入/穿透模式 |

`Fn+Tab` 调用现有的 `ensureShownAndToggleMode()`：若浮层隐藏，先以不激活应用的方式显示浮层，再切换输入/穿透状态。切换逻辑、位置保持、焦点处理和状态广播均复用现有实现。

## Fn+Tab 捕获方式

Electron 的 Accelerator 不支持 Fn 修饰键，因此 `Fn+Tab` 由现有的 macOS 原生快捷键组件识别。组件使用 Carbon 的全局热键接口注册 `kVK_Tab + kEventKeyModifierFnMask`，并请求独占处理：

- 按下 `Fn+Tab` 时只触发 Helper，不把 Tab 传给前台网页，避免输入焦点跳到下一个控件。
- 不申请“辅助功能”或“输入监控”权限。
- 原有 `Fn+Control`、`Fn+Shift`、`Fn+Option`、`Fn+Command` 仍沿用现有的修饰键状态识别逻辑，映射和触发时机不变。
- 原生组件通过标准输出发送 `tab` 事件，主进程把它分发给现有模式切换动作。

如果 macOS 拒绝注册 `Fn+Tab`，组件必须继续提供原有四组 Fn 快捷键，并单独向主进程报告 `Fn+Tab` 不可用。程序不得退回到“只检测但不拦截 Tab”的实现；此时用户仍可通过 Dock 右键菜单切换模式。

## 菜单入口

macOS 启动时不再创建 `Tray`，因此菜单栏不出现 Helper 图标。程序改为通过 `app.dock.setMenu()` 把原来的三组操作安装到 Dock 图标的右键菜单：

1. 显示/隐藏覆盖层。
2. 切到输入模式/穿透模式（标签随当前状态刷新）。
3. 退出。

普通点击 Dock 图标仍恢复主窗口。关闭主窗口仍只隐藏窗口，应用继续运行。`Command+Q`、Dock 右键“退出”和应用生命周期清理保持不变。

为避免影响其他平台，Windows/Linux 继续使用原有托盘入口；本次只在 macOS 将菜单入口迁移到 Dock。

## 错误处理与界面提示

原生组件整体缺失、不可执行或异常退出时，主窗口继续显示所有 Fn 快捷键不可用。只有 `Fn+Tab` 注册失败时，主窗口只提示 `Fn+Tab` 不可用，不影响原有四组 Fn 快捷键。

macOS 主窗口的快捷键说明增加 `fn+Tab`，并明确其作用为“输入/穿透模式”。其他平台不显示这组 macOS 专用快捷键。

## 未采用的方案

- 不使用 `Fn+中/英`：中/英键是系统输入法切换入口，会改变用户的中英文输入状态。
- 不保留 `Option+Command+X`：用户已选择由 `Fn+Tab` 作为唯一键盘入口，Dock 右键菜单继续作为备用入口。
- 不使用只轮询 `Fn+Tab` 的方案：轮询能检测但不能阻止 Tab 传给前台网页，会造成焦点移动。

## 验证

- 原生组件自检覆盖 `Fn+Tab` 事件名称、原有四组 Fn 组合和去抖行为。
- TypeScript 协议测试覆盖 `tab` 事件解析以及 `Fn+Tab` 单独注册失败时继续接收其他快捷键。
- 分发测试确认 `tab` 事件只调用现有模式切换动作，原有四组映射不变。
- 窗口管理测试确认 macOS 使用 Dock 菜单而不创建 Tray，非 macOS 仍使用 Tray。
- 菜单模板测试确认三个菜单项的动态标签和动作不变。
- 主窗口测试确认只在 macOS 展示 `fn+Tab`，且不再展示 `⌥⌘X`。
- 运行完整测试、类型检查、原生快捷键自检和生产构建。
